## A. Neutral reconstruction

### Design A — ConsumerReactor

Design A refactors the existing background loop (`ConsumerNetworkThread`) into `ConsumerReactor`, the single component that orders inputs, polls managers in a fixed order, aggregates their timing contributions into one published immutable `ReactorSchedule`, and only afterwards executes application-visible `ReactorAction`s. A manager poll returns a `PollResult` envelope of three independent outputs — `NetworkCommand` (transport intent), `ManagerEvent` (immutable cross-owner fact), and `NextPollCondition` (`PollImmediately` gated on output, finite `RetryAfter`, or `AwaitInput`) — with strict factories plus production-time validation that converts an empty-immediate result into `AwaitInput` and counts it. Cross-manager mutation is replaced on the migrated slice by an owner/fact/command discipline: a manager captures an owner-published versioned `CoordinatorSnapshot` when building a request, reports `CoordinatorUnavailableObserved(observedVersion)` through a bounded producer-local `PendingManagerEvents` buffer, and a composition-owned `ManagerCoordinationPolicy` maps the fact to `InvalidateCoordinatorIfCurrent`, which the owner applies only if the version is still current. The POC migrates the coordinator/heartbeat/commit/fetch slice, keeps legacy constructors and application-wait projections as adapters, and carries A/B benchmark evidence (idle CPU −41.5%, idle network polls −60%, no significant first-record latency change at an earlier revision) plus a real-broker coordinator-failover integration test. It deliberately does not add threads or queues, does not put domain policy in the reactor (no consumer-type branches exist in `ConsumerReactor` [fact]), and documents the remaining migration as phased work.

### Design B — Independent Readiness Kernel

Design B, produced independently from a 12-issue corpus, proposes five small primitives beside the unchanged `ConsumerNetworkThread`: `WorkReadiness` (exactly `Ready`, `At(deadline)`, `Blocked(signal)`; `Blocked` cannot yield a zero wait by construction), `ManagerReadiness` (one readiness function per kind of work; the network wait, application wait, and `poll()`'s send decision are all projections of the same predicate), `WakeupSignal`/`SignalRegistry` (named condition edges, today only `coordinator`, fired by the owner on discovery/unknown/fatal-error), and `EpochGuard` (per-component generation; completions run transport bookkeeping unconditionally but domain mutation only when the captured epoch is current). The prototype adopts the kernel in two production managers — `CoordinatorRequestManager` (one source, epoch-guarded FindCoordinator completions) and `CommitRequestManager` (two sources; the unknown-coordinator auto-commit zero of open KAFKA-20970 becomes a bounded `At(interval)`) — with exactly two documented behavior changes and eight deterministic POC tests alongside 299 unmodified regression tests. Publication ordering (F3) and reply obligations (F4) are explicit non-goals kept as per-site disciplines, and a full reactor rewrite is rejected using KAFKA-17674 as evidence that single-threading is not atomicity. The report is unusually disciplined about fact/inference/hypothesis boundaries and lists its own P0 risks, including that adoption beyond two managers is unproven.

### 2. `WorkReadiness` versus `PollResult`

**Is `WorkReadiness` a pre-poll decision while `PollResult` is a post-poll report?** Essentially yes, and that is the key to why they are not competitors. `WorkReadiness` answers "may this work run / when should it be looked at again" *before* acting; `PollResult` reports "what I produced, what facts I observed, and my next activation condition" *after* acting. B's own `poll()` demonstrates the layering: it first asks `readiness().of(...)`, then produces exactly a trunk-shaped `PollResult` [fact: both adopted managers].

**Complementary layers, competing abstractions, or duplication?** Complementary layers with **one genuinely duplicated element**: `NextPollCondition` and `WorkReadiness` are two encodings of the same fact (a manager's next activation condition). `Ready`+emit ≈ `progress(...)`; `At` ≈ `RetryAfter`; `Blocked(signal)` ≈ `AwaitInput`. The rest does not overlap: `PollResult` additionally carries facts and transport intents, which `WorkReadiness` deliberately does not; `ManagerReadiness` additionally derives the application projection from the same predicate, which A's POC still bridges via legacy `maximumTimeToWait`. A combined model must keep exactly one encoding (Section E).

**Does either make empty immediate retry impossible in production with assertions disabled?** Neither design uses Java `assert` for this [fact: grep]. A enforces it with runtime factory exceptions on the typed path plus unconditional production validation-and-conversion in `pollManager` (counted, rate-limit-logged) — this covers *every* manager in the composition, including unmigrated ones. B makes the invalid state unrepresentable *within an adopted manager's readiness function*, which is stronger where it applies and absent where it doesn't (no detection for unadopted or misclassifying managers). A protects the boundary; B fixes the source. These compose.

**Can one readiness predicate safely derive poll eligibility, network wait, and application wait?** For the two adopted managers, demonstrably yes [fact: POC tests 1–3]. Two caveats: (a) B's own `poll()` still re-derives *which* meaning of `Ready` applies (send vs drain-and-fail vs fail-on-fatal) by re-reading `coordinator()`/`fatalError()`/`closing` after the readiness gate [fact: `CommitRequestManager.poll`] — the predicate gates entry but does not carry the action, so some duplication survives; (b) whether richer managers (membership-driven heartbeat) reduce to a small source set is B's own P0 open question.

**Is `appVisible` sufficiently precise?** As a static per-source bit it is a real improvement over "every manager bounds both waits", and it fixes the concrete KAFKA-20970 projection. It is imprecise where application visibility is state-dependent (e.g., commit work is application-relevant only while an application-awaited operation is pending). In an A-style end-state the application wake is event-driven (completion actions), so `appVisible` timers should shrink to genuinely periodic application-relevant deadlines; the bit is sufficient for that narrower role [inference].

**Is `Ready` overloaded for shutdown drain-or-fail?** Yes [fact: `pendingCommitFetchReadiness` returns `Ready` for fatal-error and closing-drain cases; the report documents this deliberately]. It works, but it makes `Ready` mean "some action is appropriate" rather than "the nominal work can proceed", and pushes the disambiguation back into `poll()` — exactly the split-predicate shape the design argues against, in miniature. A tri-state (`Ready(SEND)` / `Ready(RESOLVE)`) or a separate drain source would remove the overload.

**Atomic evaluation?** Within one evaluation, yes (single-threaded). Across the loop, no: in unchanged `runOnce()`, `netWait` is computed pre-I/O from `PollResult`s and `appWait` post-I/O via `maximumTimeToWait(currentTimeMs)` *with the pre-poll timestamp* [fact], so the two projections can legitimately observe different states and the app projection uses a clock up to one network-poll stale. A's reactor recomputes and republishes the schedule post-I/O with a fresh timestamp [fact: `runOnce` post-I/O block]. Bounded impact (next iteration heals), but B inherits a sloppier evaluation discipline from trunk than its document's "cannot disagree" phrasing suggests.

**Does `poll()` still duplicate readiness conditions?** Yes, as above — B removed the *wait-side* duplicate (the F1 killer) but kept the action-selection duplicate inside `poll()`.

### 3. `WakeupSignal` versus `ManagerEvent`

- **`WakeupSignal` is only a condition edge** [fact]: no payload, no level, fires a `Runnable` (production: `NetworkClientDelegate::wakeup`). **`ManagerEvent` is an immutable fact** with payload (`observedVersion`, cause, source) routed through typed handlers to a single owner [fact].
- **Does a signal carry enough for cross-manager decisions?** No — and B does not pretend otherwise: decisions still read the peer's level (`coordinator()`). The signal solves (part of) liveness; `ManagerEvent` solves ownership and staleness. They are not competing abstractions; they answer different questions.
- **Ownership and firing coverage** are guaranteed only by convention and review: three firing sites exist for `coordinator` [fact], nothing mechanically checks edge coverage, and B's report itself flags this as P1 ("coverage is asserted, not proved").
- **Missing edge behavior**: a stall bounded by the 5 s network-poll cap plus the next manager pass — a quiet failure replacing a loud one, as B's report states plainly. The same bound applies to A's `AwaitInput` if a manager misclassifies an enabling input. **The 5 s cap is a masking backstop in both designs** [fact both docs]; neither removes it, both are honest about it.
- **Structural observation the B document does not make** [inference, high confidence]: in the current two-thread topology, signal fires that originate in network-response callbacks are *almost entirely redundant for liveness*. The selector has already returned to deliver the response that triggered the fire; `runOnce()` then re-polls **every** manager before the next wait. Discovery, mark-unknown, and fatal-error — all three current firing sites — run in response callbacks. So POC test 5 would very likely pass with the fire removed (unverified — worth the negative test in Section F). The signal's real value today is (a) documentation/traceability of the dependency, (b) future edges fired from outside the network poll (application thread, close path), (c) `fireCount` as a diagnostic. That reframes `SignalRegistry` as primarily a *diagnostics and future-proofing* channel, not a load-bearing liveness mechanism — which materially weakens the case for carrying it as a second coordination channel next to `ManagerEvent`.
- **Is `SignalRegistry` frozen and bounded by construction?** No — `signal(name)` is `computeIfAbsent` on an unbounded `HashMap`; boundedness is asserted in tests only [fact: `SignalRegistry.signal`, POC test 8]. Any typo'd name silently creates a new, never-fired signal. Freezing (enum or sealed name set, or a `freeze()` after wiring) is required before this is production-grade.
- **Compatibility constructors**: every adopting manager's legacy constructor creates a **private `new SignalRegistry()` with the default no-op wakeup hook** [fact]. Two consequences: a manager wired the old way silently loses its firing edges (fires count but wake nothing), and — worse — owner and dependent can end up on *different* registries, so `Blocked(signal)` waits on an instance nobody fires. The production share-consumer path does exactly this deliberately (fresh unbound registry) [fact: `RequestManagers` share path]; harmless today because nothing blocks on it, but it is a silent-degradation pattern with no diagnostic.
- **Can both coexist?** Not as two coordination channels. A combined model should keep `ManagerEvent` for facts/commands and reduce `WakeupSignal` to (at most) named diagnostic labels on `AwaitInput` — see Section E. Keeping both live channels would create two ways to propagate "coordinator changed", violating the prompt's own de-duplication rule.
- **Does every `Blocked(signal)` name the actual enabling condition?** No. `CoordinatorRequestManager` returns `Blocked(coordinator)` for *four distinct conditions*: closing, already-discovered, and **request-in-flight** — where the true enabling input is the in-flight request's completion, not a coordinator-level change [fact: `findCoordinatorReadiness`]. The in-flight case never gets a `coordinator` fire on plain response arrival that doesn't change the level (e.g., a retriable failure fires nothing; liveness is provided by the loop re-poll after the response, not by the named signal). The label is therefore diagnostic-approximate, not precise. Same for `pendingCommitFetchReadiness`'s "nothing queued" branch, which is blocked on "an application submits work", not on the coordinator.

### 4. State ownership and stale work

Scenario: `request captures coordinator/version C7 → coordinator becomes unknown → C9 published → the C7 response arrives`.

**Design A** [fact, traced end-to-end]: heartbeat/commit capture `CoordinatorSnapshot(node, version=7)` at build time (`AbstractHeartbeatRequestManager:344`, `CommitRequestManager:1041`); the failure observation is buffered producer-locally with greatest-version-wins (`PendingManagerEvents.add`); routed as `CoordinatorUnavailableObserved(observedVersion=7)` → `InvalidateCoordinatorIfCurrent`; **final validation occurs in the owner**, `CoordinatorRequestManager.handleCoordinatorUnavailableObserved`, which ignores the event because `7 != 9` (`coordinatorVersion` is bumped both on unknown and on discovery of a different node). C7 cannot invalidate C9. Structural prevention on the migrated slice.

**Design B** [fact]: `EpochGuard` fences only **FindCoordinator's own completions** (snapshot at `makeFindCoordinatorRequest`, advance on `signalClose`/`markCoordinatorUnknown`, transport bookkeeping always, domain mutation gated). The C7→C9 scenario as posed, however, arrives through a *peer's* completion: on `f5b39cba42`, `CommitRequestManager` (lines 1056, 1409) and `AbstractHeartbeatRequestManager` (389, 399) still call `coordinatorRequestManager.markCoordinatorUnknown(...)` unconditionally on NOT_COORDINATOR/COORDINATOR_NOT_AVAILABLE. **A delayed C7-era error response will invalidate C9**, advance the epoch, fire the signal, and force an unnecessary rediscovery. This is retained trunk behavior, not a regression B introduced, and B never claims to fix it — but it means B's stale-work story covers the self-owned path only, and its answer to the prompt's scenario is "not prevented; converted into a transient extra discovery cycle" [fact for the mechanism; the extra-cycle consequence is inference]. The `EpochGuard` mechanism *could* cover it (commit captures the coordinator epoch at build; the invalidation call checks currency), but that is precisely reinventing A's `CoordinatorSnapshot.version` — evidence the two mechanisms want to be one (Section E).

**Direct peer reads** (`coordinator()`, `fatalError()`): present in both designs' managers [fact: greps on both branches]; single-threaded, so not data races, and *within* one manager pass no owner mutation interleaves (A defers commands across the boundary; B mutates only in callbacks) — so the view is coherent per pass in both. They remain implicit dependencies; A has a stated migration rule to eliminate cross-owner *mutation* (done) and eventually reads (pending); B keeps reads by design and documents them in an ownership table.

**Is `EpochGuard` appropriately scoped?** As a component-generation guard it is correct and cheap, and its transport/domain split is a genuinely good discipline that A's design does not state as crisply. It is **too coarse** for operations whose validity is scope-bound (an offset fetch's partition working set — B's own Table 6 says so) and **insufficient** for cross-owner observation fencing (above). A's owner-version snapshot is the same counter idea, but attached to the *published* truth and carried across the manager boundary, which is what the cross-owner case needs. One mechanism, two access patterns.

### 5. Global ordering

**Does the Readiness Kernel guarantee the A-style sequence** (inputs → ordered pass → publish state+schedule → app-visible actions → network poll)? No, and it does not try to: `runOnce()` is unchanged, so events are processed, managers polled, requests staged, network polled, then `cachedMaximumTimeToWait` published — with background events, future completions, and fetch-buffer signals still published from wherever they occur, before or after the wait value [fact]. B's position is that publication ordering is a per-site discipline (non-goal). **Which of A's guarantees are actually required?** The corpus itself argues that at least two are: (a) *publish-before-wake* — KAFKA-20397 is precisely a completion published without a wake edge into an already-computed wait, and KAFKA-20854's fix hand-built publish-then-wake-once for the fetch path; (b) *deadline monotonicity across managers* — an early return must not let one manager's fresh result postpone another's retained deadline; A implements this in `ManagerPollCache.preservePendingDeadline` [fact]. In B, (b) is moot *as long as* every iteration recomputes all readiness functions from scratch (fresh min each pass, nothing retained) [fact] — B gets the property by recomputation rather than retention, at the cost of not being able to cheaply skip work. (a) B genuinely lacks, and its own P1 (20397 edge unimplemented) concedes the consequence.

**Is `ConsumerReactor` at risk of becoming a God object?** By responsibility, no: domain policy lives in composition-owned handlers, there are no consumer-type or manager-type branches [fact], and actions are opaque closures. By mechanism density, it is the most intricate class in either design [judgment]: three phases with *different* command-application rules (INPUT applies, PRE_IO defers-with-error-log, POST_IO defers), `affectedManagers` post-I/O re-poll with marks deliberately discarded by the next full pass, one-shot legacy application-deadline delivery threaded through both the cache and the schedule, and close-time re-publication. Each rule has a documented reason, but the correctness argument lives in comments and the KIP rather than in types. Separating the five concerns the prompt lists: generic orchestration mechanics (reactor, appropriately), manager-local policy (managers, correct), consumer-variant composition (RequestManagers, correct), cross-manager coordination policy (`ManagerCoordinationPolicy`, correct), app-visible effect ordering (reactor, appropriately). The layering is right; the residual risk is phase-rule complexity, not misplaced policy. The PRE_IO deferred-command path is containment, not correctness, and A says so itself [fact: code comment + KIP].

Per the prompt's instruction: the rejection of a maximal single-owner rewrite (B's Alternative B, rejected via KAFKA-17674) is **not** evidence against Design A — the actual A branch keeps the two-thread topology, does not confine all state, and does not move the fetch hot path [fact]. B's rewrite rejection and A's actual shape are compatible positions.

### 7. Operational qualities

- **Debugging / why-is-work-waiting**: B is stronger per manager — `WorkReadiness{BLOCKED on coordinator}` and per-source names are directly loggable answers, `fireCount` separates lost from eager wakeups. A is stronger per iteration — schedule generation, deadline source, action reasons, and four production counters give causal traces across managers. Combined they'd be excellent; individually each covers half the question. (Caveat from §3: B's `Blocked` labels are approximate.)
- **Reconstructing one operation across retries**: A documents the identity model and keeps futures as identity; B's trace-point list (plan/emit/epoch/completion/edge/re-plan) is good for one manager's work but has no cross-manager thread to pull. Slight edge A.
- **Bounded CPU/memory**: both bounded. B is allocation-lighter per iteration (a couple of small value objects; `Ready` shared) [fact]; A allocates several lists/copies/snapshots per phase per iteration [fact] yet still measured a −41.5% idle CPU improvement at the benchmarked revision [fact, historical]. Saturated-throughput allocation for A is unmeasured (its own benchmark doc says so).
- **Testability**: both strong and deterministic. A: 1205-line `ConsumerReactorTest` plus component/integration layers including a real-broker failover test. B: 8 pinned invariant tests + untouched regression suites, deliberately driving the real loop shape by hand. B's harness is simpler to reason about; A's covers far more surface.

- **Migration and rollback**: B wins decisively — per-manager opt-in, two documented behavior changes, zero loop changes, trivially revertible. - **Compatibility risk**: B near-zero today; A moderate (thread name, metrics, and API preserved [fact], but the wait-projection change is behaviorally observable).
- **Future variants**: A structurally better prepared (no type branches, composition policy); B unproven but plausibly adoptable per manager.

## C. Findings (severity order)

Test execution on the pinned commits (this review's own runs): Design A reactor suites 58/58 green, Design B `ReadinessKernelPocTest` 8/8 green — details in Appendix 1.

1. **[High / Design B / verified fact]** Peer-observed coordinator invalidation is unfenced: `CommitRequestManager.java:1056,1409` and `AbstractHeartbeatRequestManager.java:389,399` (branch `fable/independent-async-consumer-design`) call `coordinatorRequestManager.markCoordinatorUnknown(...)` unconditionally from response handlers. A delayed error response captured against coordinator C7 arriving after C9's discovery invalidates C9, forcing a spurious rediscovery and interrupting heartbeat/commit progress. `EpochGuard` does not cover this path (it guards only FindCoordinator's own completions). Retained trunk behavior, but it means B does not answer the review's central staleness scenario; A does (`CoordinatorRequestManager.handleCoordinatorUnavailableObserved`, version compare).
2. **[High / Design B / verified fact]** `SignalRegistry` is bounded and frozen only by convention: `SignalRegistry.signal()` is `computeIfAbsent` on an unbounded map; compatibility constructors (`CoordinatorRequestManager`, `CommitRequestManager`) create private registries with the default **no-op** wakeup hook, and the production share-consumer path deliberately wires a fresh unbound registry (`RequestManagers` share branch). A dependent blocked on a signal from a different or unbound registry waits on an edge that never fires, degraded silently to the 5 s cap with no diagnostic.
3. **[High / Design A / verified fact, self-admitted]** Cross-owner facts first produced in the PRE_IO pass are containment, not correctness: `ConsumerReactor.stageManagerEvents` logs an error and defers the command, but transport work already built in the same pass from the stale owner view cannot be replayed or cancelled (`ConsumerReactor.java:476-484`; KIP status table row "Cross-owner fact admission"). Until producers are constrained to the input/post-I/O admission paths, "publish before build" holds by construction only for callback-produced facts.
4. **[Medium / Design B / inference]** In the current topology, all three existing `coordinator` signal firing sites run inside network-response callbacks, after which the selector has already returned and `runOnce()` re-polls every manager anyway; the fires are therefore largely redundant for liveness (POC test 5 would likely pass with the fire removed — unverified). The kernel's load-bearing fix for the corpus bugs is `WorkReadiness`, not `WakeupSignal`; the signal is primarily a diagnostics/future-proofing channel and should be evaluated (and priced) as such.
5. **[Medium / Design A / verified fact, self-admitted]** The KAFKA-20970-shape legacy application-wait zero from `CommitRequestManager`/`StreamsGroupHeartbeatRequestManager` is *contained* (one-shot expired-deadline delivery via `ManagerPollCache`/`deliverExpiredApplicationDeadline`), not eliminated; B deletes the zero at its source for the same manager. A's own KIP lists eliminating these as remaining migration work.
6. **[Medium / both / verified fact]** The 5000 ms network-poll cap remains the backstop for a missing enabling input in both designs (`AwaitInput` misclassification in A; missing signal edge in B). Both documents acknowledge it; neither design detects a *specific* missed edge, so both convert loud spins into quiet ≤5 s stalls.
7. **[Medium / Design B / verified fact]** The two readiness projections are evaluated at different times with a stale timestamp in the unchanged loop: `ConsumerNetworkThread.runOnce` computes `maximumTimeToWait(currentTimeMs)` after network I/O using the pre-poll clock. The "cannot disagree" property holds per evaluation, not across the iteration; the application deadline can be over-estimated by up to one network-poll duration. (Trunk-inherited; A's reactor republishes post-I/O with a fresh clock.)
8. **[Low / Design B / verified fact]** `Ready` is overloaded (send vs drain-and-fail vs fail-on-fatal) and `poll()` re-derives the distinction by re-reading peers — a small survival of the split-predicate pattern the design targets; `Blocked(coordinator)` labels several conditions whose true enabling input is not a coordinator-level change (in-flight completion; application submission).
9. **[Low / Design A / judgment]** `ConsumerReactor`'s phase machinery (three phases with different command rules, discarded post-I/O marks, one-shot deadline delivery) is the highest-complexity artifact in either design; policy placement is clean (no domain or type branches — verified), but the correctness of the phase rules rests on comments and the KIP rather than on types, which is a maintenance risk for exactly the contributor population both documents worry about.
10. **[Low / Design A / verified fact]** The POC removed application-side assignment/position rescans, making liveness depend on every corresponding wake/completion signal being published; the KIP flags the proof obligation (Phase 2 exit), and the integration evidence today is one real-broker failover test plus component tests — not yet the per-input liveness suite the KIP requires.

## D. Architectural recommendation

**Combine them as distinct layers.** Neither is a substitute for the other, and the overlap is small and removable:

- Design B's `ManagerReadiness`/`WorkReadiness` is the right **manager-local layer**: it is the only mechanism on the table that makes the recurring F1 divergence (five-plus sites over two years, one still open) *unrepresentable at the source*, and its per-manager, two-behavior-change migration is the cheapest reviewable unit Kafka can land. Its invariants are local by nature — nothing in it orders effects across managers, fences cross-owner observations, or publishes an aggregate wait.
- Design A's reactor boundary is the right **cross-manager layer**: owner-versioned snapshots with owner-side fencing (the only answer to C7→C9), publish-before-effect with a generation counter (the only mechanism addressing the KAFKA-20397/18641/20854 ordering class), composition-owned event policy (the only variant-extensibility structure), and production-boundary validation that protects the composition from managers that have not yet adopted the local discipline.
- The workflows compose naturally: a manager computes its readiness once (B), projects it into the typed `PollResult` condition (A) and emits facts with captured owner versions (A); the reactor aggregates, publishes, fences, and orders effects (A); the application projection comes from `appVisible` sources (B) plus completion actions (A).

This is a decision on invariants, not class counts: B supplies invariant I1 (readiness soundness) at the source; A supplies I3/I4 (stale-work fencing across owners, publish-before-effect) which B explicitly declines to own; both need each other's half. Adopting either alone leaves documented, recurring failure families with no mechanism: A alone keeps containing (not removing) per-manager wait divergence during a long migration; B alone leaves effect ordering, cross-owner staleness, and app-side lost wakeups as per-site conventions — the exact convention-dependence both corpora indict.

**Not recommended**: adopting B's `WakeupSignal`/`SignalRegistry` as a live coordination channel alongside `ManagerEvent` (two channels for one fact class; see Finding 4 and Section E), or A's current plan of migrating legacy `maximumTimeToWait` projections manager-by-manager *without* B's predicate unification (that path reproduces per-site guard-mirroring under a new name).

## E. Smallest coherent combined model

One representation per fact; one coordination channel; one version counter per owner.

**API (all internal):**

```java
// Manager-local (from B, with the Blocked payload changed)
WorkReadiness = Ready | At(deadlineMs) | Blocked(Await cause)   // cause: enum/name, diagnostic only
ManagerReadiness { addSource(name, appVisible, fn); of(name, now); netWaitMs(now); appWaitMs(now); }

// Manager output (from A; NextPollCondition subsumed by WorkReadiness)
PollResult { List<NetworkCommand>, List<ManagerEvent>, WorkReadiness nextPoll }
  // strict factories: empty output ⇒ nextPoll may not be Ready; production boundary validation retained

// Cross-manager (from A, absorbing EpochGuard)
OwnerVersion { snapshot(); advance(); isCurrent(v); }            // one per state owner
OwnerSnapshot(ownerState…, version)                              // e.g. CoordinatorSnapshot
ManagerEvent(type, source, observedOwnerVersion, payload…)
ManagerCoordinationPolicy / CoordinationPlan / ManagerCommand / ReactorAction / ReactorSchedule — as on branch A
```

**Ownership of decisions:** the manager owns its readiness predicates and domain rules; the state owner owns version advancement and final staleness validation (both for its own completions — B's transport/domain split verbatim — and for peer observations — A's version compare); the composition owns event policy and variant selection; the reactor owns ordering, aggregation, publication, and effect execution; the transport owns correlation and timeouts.

**Request lifecycle:** readiness `Ready` → build request, capture `OwnerVersion.snapshot()` of every consumed owner snapshot → transport → completion runs transport bookkeeping unconditionally; own-state domain mutation iff own version current; peer observations emitted as versioned `ManagerEvent`s into the producer-local latest-only buffer → drained at the input boundary → policy → command → owner validates version → full ordered pass rebuilds dependent work → schedule published → actions execute.

**Wakeup lifecycle:** network-thread liveness = finite `At` deadlines + network completions + application-event enqueue wakeups + the bounded cap (unchanged); no per-condition signal channel — the full per-iteration pass is the propagation mechanism, and `Blocked(cause)` names the enabling input for logs and for a `blocked-with-no-edge` diagnostic. Application-thread wakes exist **only** as `ReactorAction`s executed after publication, coalesced, last.

**Stale-response lifecycle:** one monotonic version per owner; own completions and peer observations both validate against it at the owner; producer-local buffers are latest-only and never authoritative; in-flight work retains versions, never snapshot history.

**Publication-before-effect boundary:** A's rule verbatim — apply owner state, publish state + `ReactorSchedule` (generation++), publish staged background events, then execute actions with the wake last. `appWaitMs` over `appVisible` sources replaces the `usesLegacyApplicationWait` bridge as managers adopt, and the one-shot expired-deadline containment is deleted per manager once its projection is readiness-derived.

Deliberately absent, with reasons: `WakeupSignal`/`SignalRegistry` as live objects (redundant channel in this topology — Finding 4; keep only the *names* on `Blocked`); a separate `EpochGuard` class (same counter as the owner version — Section 4); `NextPollCondition` (same fact as `WorkReadiness`); any dynamic dependency graph, event bus, or new thread (neither corpus justifies one).

## F. Validation plan

Minimum bounded slices and deterministic tests before changing the KIP or merging either design (all runnable with `-da`, no Java asserts anywhere in the contract path):

1. **Empty immediate retry, assertions disabled**: (a) adapter-constructed `PollResult(0)` with no output → reactor converts to input-wait, increments `reactor-poll-result-contract-violation-total`, network poll timeout stays positive across 10 iterations; (b) B-side negative control: a readiness function misclassified as `Ready` with no emitted work → demonstrate the composition-level guard is what catches it (this is the test that justifies keeping A's boundary validation in the combined model).
2. **Real enabling signal and missing-signal behavior**: for one blocked condition, (a) prove the level change is observed by the next full pass with **no** dedicated wakeup edge (establishes the loop, not the signal, as the propagation mechanism — resolves Finding 4 empirically, e.g. by removing the `coordinatorSignal.fire()` calls and re-running B's POC test 5); (b) prove a genuinely missed edge degrades to a bounded ≤5 s stall and is surfaced by a `blocked-with-no-edge` diagnostic rather than silence.
3. **C7 response after C9 publication**: deterministic `MockClient` test — commit request built against C7; C7 marked unknown; C9 discovered; delayed NOT_COORDINATOR response for the C7 attempt delivered; assert C9 is retained, no rediscovery is scheduled, and the commit retries against C9. Run the same test against baseline/B to pin the current failure (rediscovery forced).
4. **Heartbeat and membership adoption dry run**: express `AbstractHeartbeatRequestManager`'s wait/eligibility as readiness sources (interval, backoff, pollTimer, coordinator-known, skip states) with membership driving reconciliation from `poll()` unchanged; exit criterion is source count and no readiness function needing peer *mutation* — this resolves B's P0 and A's driver-boundary claim with one slice.
5. **Fetch in-flight completion and application wakeup**: every fetch completion class (success, empty, session error, disconnect, preparation failure) produces exactly one post-publication wake with the schedule generation advanced before the wake (extends A's existing fetch-fact tests; supplies B's missing 20397 edge for the buffered-data condition).
6. **Shutdown with pending coordinator-dependent work**: one scenario combining B's test 7 and A's close drain — pending commit + unknown coordinator + staged async-poll completion at close: commit futures fail deterministically with the KAFKA-19357 exception, the staged completion is still delivered, no FindCoordinator is generated after the close signal, and a post-close stale completion mutates nothing.
7. **Publish-before-application-visible-effect ordering**: generation assertions on commit terminal completion and background-event publication (extend A's existing schedule-generation checks beyond the fetch path).
8. **Regular/share/Streams composition boundaries**: construction test that the share and Streams compositions build with the combined wiring (no unbound-registry analogue possible by construction), an architecture test that the reactor contains no consumer-type branches, and one Streams-heartbeat adoption slice (the second half of open KAFKA-20970).
9. **Performance gate re-run** (before migration acceptance, per A's own benchmark doc): paired A/B run at candidate HEAD including saturated throughput and allocation-per-record, not just idle/first-record.

## G. Do not claim yet

- That the readiness vocabulary fits heartbeat/membership/share managers without contortion — unproven in both designs (B's own P0; A migrated heartbeat's *events* but kept guard-style eligibility and did not unify its wait projection).
- That either design fixes KAFKA-20397 — B explicitly does not; A has the ordering mechanism and staged metadata-error actions, but no deterministic 20397 reproduction was found in A's unit suites on the pinned commit (grep for the ticket returns none), and the KIP's own test plan still lists the liveness proof as an exit criterion.
- That `WakeupSignal` improves liveness in the current topology — untested either way (Finding 4 is inference until validation item 2a runs).
- That A's benchmark numbers hold for the current POC HEAD or under saturated throughput/allocation profiles — the benchmark doc itself scopes them to revision `032899a6ab`, idle and first-record only.
- That B's 307 green tests demonstrate architectural completeness — they demonstrate that two adopted managers preserve behavior except for two documented changes, exactly as its own report scopes.
- That A's full phase machinery (PRE_IO/POST_IO deferral rules, affected-manager re-poll) is the minimal sufficient mechanism — no simplification experiment has been run against a composition where all managers are readiness-adopted [hypothesis: several phase rules exist to contain legacy producers and may shrink].
- That either design improves (or harms) end-to-end latency/throughput under load — no evidence beyond A's bounded idle-profile run.
