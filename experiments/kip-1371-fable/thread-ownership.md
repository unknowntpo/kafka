# KIP-1371 C5：執行緒歸屬契約（thread ownership）

對象：`AsyncKafkaConsumer` 與其共用物件，以 branch `fable/kip-1371-event-loop` HEAD（`f9deb8bdab`）為準。
路徑縮寫：`I/` = `clients/src/main/java/org/apache/kafka/clients/consumer/internals/`，`E/` = `I/events/`。
執行緒代號：**app** = 呼叫 consumer API 的應用執行緒；**net** = `ConsumerNetworkThread`；**any** = 任意使用者執行緒（只有 `wakeup()`）。

## 3. C5 規則

1. **Manager 狀態只在 network thread。** `RequestManager` 的所有欄位（`pendingRequests`、`closing`、`coordinator`、`MemberState`、`inflightRequests`、`requestsToRetry`、`pendingOffsetFetchEvent`、`cachedUpdatePositionsException`…）只由 `ConsumerNetworkThread` 讀寫；app thread 與它們的唯一介面是 `ApplicationEvent`（入 `applicationEventQueue`）與 event 的 `CompletableFuture`。`signalClose()` 也只透過 `CommitOnCloseEvent`／`StopFindCoordinatorOnCloseEvent` 在 net 執行（`E/ApplicationEventProcessor.java:484-508`）。例外：`ConsumerNetworkThread.cleanup()` 在 net 執行，但由 app 的 `join()` 等待——這是唯一 app「看見」manager 終局的點，且只透過 reaper 失敗的 future。
2. **User callback 只在 application thread。** `ConsumerRebalanceListener`（`I/ConsumerRebalanceListenerInvoker.java`）、`StreamsRebalanceListener`、`OffsetCommitCallback`（`I/OffsetCommitCallbackInvoker.executeCallbacks`）、`ConsumerInterceptor`、`AcknowledgementCommitCallback`（Share）都在 app thread 執行：一般路徑在 `poll()`／`commitSync()`／`updateAssignmentMetadataIfNeeded`／`close` 內（`I/AsyncKafkaConsumer.java:1025-1026`、`:1153`、`:1863`、`:2144-2154`、`:1721-1758`）。net 端絕不直接呼叫 user code；它只 enqueue（`I/ConsumerMembershipManager.java:415-448`、`I/CommitRequestManager.java:445`）。
3. **App 對背景 future 的完成一律經 `*CallbackCompletedEvent`。** `PartitionsAssignedEvent`／`PartitionsRemovedEvent`／Streams `*CallbackNeededEvent` 的 `future` 由 net 建立並由 net 完成：app 跑完（或跑失敗）callback 後送 `ConsumerRebalanceListenerCallbackCompletedEvent`／`StreamsOnTasks*CallbackCompletedEvent`（`I/AsyncKafkaConsumer.java:275-287`、`:2504-2537`），net 在 `consumerRebalanceListenerCallbackCompleted`（`I/ConsumerMembershipManager.java:452-474`）完成它。app 不得直接 `complete`——唯二例外是 (a) 無 listener 時 `event.future().complete(null)`（`:241-242`，此時沒有 user code，故無須回報）與 (b) close 步 9 的 reaper `completeExceptionally`（此時 net 已結束，無人等待）。`WakeupException`／`InterruptException` 也不例外：KAFKA-18160 之後 `invokeRebalanceCallbacks` 把它們包進 completed event 的 `error` 再 rethrow（`TerminationContractTest.testCallbackWakeupOrInterrupt*` 釘住三種 callback）。
4. **Position 的 writer 是 application thread（`FetchCollector`），例外是在 net 執行、但 app 阻塞在 API 呼叫內的 seek／reset。** 常態推進：`FetchCollector.fetchRecords` 先 `subscriptions.position(tp, next)` 再回傳 records（`I/FetchCollector.java:185`，app）。其餘 position 寫入（`seekUnvalidated`／`seekValidated`／`requestOffsetReset`／`resetInitializingPositions`／`maybeSeekUnvalidated`／`completeValidation`）都在 net，且發生在 (a) app 阻塞於 `addAndGet(SeekUnvalidatedEvent／ResetOffsetEvent／CheckAndUpdatePositionsEvent)`，或 (b) partition 尚無 position（initializing／awaiting reset）、app 不會對它 `position(tp, next)` 的時候（`isFetchable` 為 false，`FetchCollector:155-162` drain）。C3 的 autocommit 快照（`committableOffsets`）因此只在 app thread 讀 `allConsumed()`；net 端讀 `allConsumed()` 只剩 `AsyncCommitEvent`／`SyncCommitEvent` 無 offsets 的路徑（app 阻塞等 `offsetsReady`）與舊版 `updateTimerAndMaybeCommit(long)`（`AssignmentChangeEvent`，app 阻塞）。
5. **推論：任何欄位若 writer 只有一個 thread、reader 在另一個 thread，最少要 `volatile`／`Atomic*`；若兩個 thread 都寫，必須是同一把鎖或 queue。** 表 §1–§2 中唯一違反的是 `SubscriptionState.seekUnvalidated`（§1.3）。
